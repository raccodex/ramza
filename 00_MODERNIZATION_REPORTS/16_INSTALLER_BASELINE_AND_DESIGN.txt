2. Current Installer Flow
-------------------------
Public entry point:
- install/index.php

Current page flow:
1. terms
2. req
3. installation
4. finish

Routing method:
- GET parameter page selects one of terms, req, installation, or finish.
- The installer has no server-side session-backed step state.
- Direct page navigation/skipping is possible.
- There is no CSRF protection.
- There is no install/install.lock detection or creation.

Current install submission:
- A single POST to ?page=installation with hidden field install=install performs
  database connection, config writes, .htaccess write, SQL import, configuration
  updates, administrator insert, chmod calls, and success redirect.

7. Current Licence Behaviour
----------------------------
Current installer functions:
- check_($check)
- check_success($check)

Observed behaviour:
- Both functions return local SUCCESS arrays.
- No real remote endpoint is called by the current installer.
- The submitted purchase code is written into config.php and nodejs/config.json.
- A second success check is called after SQL import.

Critical Phase 2G finding:
- The current installer contains hard-coded local success behaviour. This is an
  existing security defect, not acceptable behaviour to preserve.
- The rebuild must not copy this bypass or make production verification return
  fake success.
- A narrow license adapter must be introduced. Production behaviour must call a
  legitimate verification contract once that contract is known and safe to use.
- Tests may simulate invalid/network/TLS/malformed responses only at the adapter
  boundary and must not make the production adapter succeed falsely.

Related non-installer license/update endpoints found:
- xhr/check_for_updates.php uses a ramza.com update-check URL with purchase_code
  in a query string.
- xhr/download_updates.php uses ramza.com update/download URLs with purchase_code
  in query strings.
- xhr/admin_setting.php contains mobile/native access-token calls.

These update/mobile endpoints are not a safe substitute for installer purchase
verification without an explicit supported contract.

8. Current Database Mutations
-----------------------------
On install submission after initial validation:
- Connects to MySQL with submitted credentials.
- Reads @@sql_mode and blocks strict_trans_tables and only_full_group_by.
- Writes config.php and nodejs/config.json before SQL import.
- Copies htaccess.txt to .htaccess when present.
- Imports ../ramza.sql, which is missing in this repository.
- Calls the second hard-coded success check.
- Updates Wo_Config.is_ok to 1 on success.
- Drops Wo_Config and Wo_Users when the second success check does not set can=1.
- Generates widnows_app_api_id with md5(microtime()).
- Generates widnows_app_api_key with md5(time()).
- Updates siteName, siteTitle, and siteEmail.
- Inserts the initial administrator into Wo_Users using sha1(admin_password).
- Does not insert a companion Wo_Users_Fields row for the administrator.
- Sets seoLink to 0 if apache_get_modules exists and mod_rewrite is absent.

Critical mutation risks:
- Config files are written before database import/post-import completion.
- License failure path drops tables.
- SQL import can partially apply DDL and leave no reliable recovery state.
- No prepared statements are used for installer-controlled updates/inserts.
- No retry/idempotency guard prevents duplicate administrator creation.

9. Authentication And Password Compatibility
--------------------------------------------
Wo_Login():
- Located in assets/includes/functions_one.php.
- Detects md5, sha1, and 60-character password_hash values.
- Uses password_verify() for password_hash values.
- Upgrades md5/sha1 passwords to password_hash() after successful legacy login.

Registration:
- User creation path in assets/includes/functions_one.php uses password_hash()
  with PASSWORD_DEFAULT.
- Registration also inserts a Wo_Users_Fields companion row.

Password reset/update:
- Wo_ResetPassword() uses password_hash() with PASSWORD_DEFAULT.
- xhr/update_user_password.php uses password_hash() with PASSWORD_DEFAULT.
- xhr/update_new_logged_user_details.php uses password_hash() for new password.

Decision:
- The rebuilt installer should create the initial administrator with
  password_hash($password, PASSWORD_DEFAULT), not sha1().
- The real login path is compatible with that hash form.
- The rebuilt installer should create required companion user/profile rows where
  the existing registration contract requires them.

10. Installation/Reinstallation Detection
-----------------------------------------
Current installer:
- Does not check install/install.lock.
- Does not create install/install.lock.
- Does not treat an existing non-template config.php as installed.
- Does not query for core tables before import.
- Can replay while a local config.php exists.

Runtime/admin status:
- assets/includes/functions_one.php getStatus() reports an error when ./install
  exists and tells the owner to delete or rename it.
- This is advisory only and does not prevent installer replay.

Required rebuild behaviour:
- Block when install/install.lock exists.
- Block when a non-template config.php contains usable settings.
- Block when submitted database contains existing/core application tables.
- Never provide a GET/query-string unlock or bypass.

12. Current UI/UX Contract
--------------------------
Current installer UI:
- Single legacy install/style.css file.
- Imports a Google Font remotely.
- Uses legacy ramza wording, title, favicon/theme paths, and success copy.
- Uses Bootstrap-era classes and jQuery from a theme path.
- Has a four-step horizontal indicator.
- No accessible error summary or aria-live progress.
- No keyboard/focus design beyond browser defaults.
- No responsive/mobile-specific modern redesign found beyond legacy CSS.
- No reduced-motion or dark-mode support.
- Completion uses an animated confetti SVG.

Required rebuild UI:
- Original RACSocial branding.
- Local assets only, no CDN/remote fonts.
- Responsive desktop/tablet/mobile.
- Accessible stepper, labels, descriptions, focus states, error summary, and
  aria-live progress.
- Vanilla JavaScript where practical with safe no-JS form fallbacks except where
  chunked progress requires JavaScript.
- Real progress, not simulated progress.

14. Proposed Installer Flow
---------------------------
1. Welcome and license terms
2. Server requirements
3. Database connection
4. Site configuration
5. Administrator account
6. Review and confirmation
7. Installation progress
8. Completion and security guidance

Design decisions:
- Server-side validation at every step.
- Installer-specific session with HttpOnly, SameSite=Lax, secure when HTTPS.
- Per-form CSRF tokens using constant-time comparison.
- POST/Redirect/GET for normal forms.
- Strict server-side step state; hidden fields are not proof.
- Never repopulate database password, purchase code, or administrator password.
- Duplicate install submission guarded by server-side state and lock/progress.
- Sensitive state cleared after success or terminal failure.

15. Compatibility Decisions
---------------------------
Preserve:
- install/index.php as public entry point.
- Existing database schema and table names.
- Config variable names expected by bootstrap.
- Existing application routes and auth/API contracts.
- Wo_Config keys including legacy spelling widnows_app_api_id/key.
- Existing one-domain license terms where applicable.
- htaccess.txt rewrite contract.

Modernize:
- PHP runtime floor is PHP 8.2.0.
- Administrator password uses password_hash().
- API/application keys use random_bytes().
- SQL import uses robust parser/progress and wowonder.sql.
- Config and Node JSON generation use safe serialization/encoding and atomic
  temp-write-plus-rename activation.
- Requirements are classified as required/recommended/environment, not static
  fake checks.
- Error handling uses concise browser errors plus redacted protected logs.

17. Phase 2B Exit Criteria
--------------------------

important risk carried forward:

- The current installer does not contain a legitimate production license
